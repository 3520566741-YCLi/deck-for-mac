# 让语音助手回答得更快（说完到出声 2–3 秒）

**中文** · [English](voice-latency.en.md)

把下面全部内容连同你的项目一起贴给你的 AI 编程助手（Claude Code、Cursor 等）。

---

请帮我缩短语音助手的响应延迟：从我说完话到它开始出声的时间。参考下面这套方案。它跑在 Apple 芯片的 Mac 上，从说完到第一声大约 **2–3 秒**；优化前要 5–6 秒。把我的流程和它对比，先测量，再先修差距最大的地方。

## 参考架构

本地优先，只有大模型在云上。

| 环节 | 用什么 | 在哪跑 | 典型用时 |
|---|---|---|---|
| 唤醒词 | sherpa-onnx 关键词检测（zipformer 中英 3M，int8），多种叫法；声纹（3D-Speaker CAM++）作软门槛 | 本机 CPU | 0.2–0.4 秒 |
| 按键说话 | 一个硬件键：按住说、松开结束（不用等静音） | 原生小助手 | 0 秒 |
| 收音 | 小的原生应用（Swift，AVAudioEngine）。16 kHz 单声道 float，每块 100 ms，经本机 TCP 发给 Python 服务。10 秒环形缓冲，保留 0.4 秒预录，不吃第一个字 | 本机 | — |
| 判断说完 | Silero VAD（经 sherpa-onnx），句尾静音 0.6 秒 | 本机 CPU | 0.6 秒 |
| 实时字幕 | Apple 本机语音识别（只用中间结果，说话时显示） | 本机 | 流式 |
| 最终文字 | Qwen3-ASR 0.6B int8（经 sherpa-onnx，4 线程），产品名做热词；再过一个小纠错表和繁转简（OpenCC） | 本机 CPU | 每句 0.4–0.8 秒 |

| 播放 | 同一个原生小助手（AVAudioPlayerNode），一块接一块排好，中间不留空 | 本机 | — |

## 大脑、记忆和电脑操作怎么配合

**只有一个大脑：DeepSeek。** 用户说的（语音或打字）都进同一个 DeepSeek 对话循环，流式 + 工具调用。语音层只负责语音转文字、文字转语音，自己不做任何决定。模型能调的工具：
- 界面工具：读、打开、关闭控制台卡片，切换页面，换深浅色，换声音或语速
- 记忆工具：`memory_save`、`memory_update`、`memory_delete`、`recall`
- 网页工具：`web_search`（DeepSeek 自带的搜索接口）和 `read_page`
- 屏幕工具：`screen_look`、`screen_click`、`screen_type`、`screen_key`、`screen_open`、`screen_scroll`、`screen_confirm`
- 清理扫描，确认那一步只在用户说「好」之后才执行

**长期记忆（借鉴 mem0，但省钱）。**
- 存储：一个小 SQLite 文件，放记忆、聊天记录（保留最近 3000 条）和用量统计。几百 KB，不用向量数据库，不用额外服务。
- 怎么写记忆：
  - 回答问题的那一次大模型调用，顺手用工具维护记忆。没有第二次「提取记忆」调用，不加延迟也不加钱。
  - 每条记忆是一句简短的第三人称句子（比如「用户喜欢……」）。
  - 稳定的事实（偏好、决定、人、项目、规矩）就新增；事实变了或重复了就更新；用户说「忘掉」或过时了就删除。一次性的细节不存。
  - 存了东西会在回答里简短提一句，界面上给一个撤销按钮。
- 怎么读记忆：
  - 最多 120 条记忆直接放在系统提示的固定部分，模型总能看到，也让缓存前缀保持稳定。
  - 最近 24 轮对话作为历史。
  - 更早的细节由模型调用 `recall`，在聊天记录和记忆里按关键词搜。
- 被打断的轮次也会存下来，标成「已停止」，模型以后不会回头去补答过时的问题。

**电脑操作：DeepSeek + Jev（快速选择模型）+ 原生「手」应用。**
- DeepSeek 决定*要不要*做、*做什么*，比如「在邮件里点发送按钮」。
- 一个小的 macOS 原生应用（Swift，辅助功能 API）读出前台应用的可点击元素，真正去点、输入、按键。Python 通过本机 Unix socket 和它通信。
- 挑哪个元素这一步，让大模型做通常很慢。我们用 **Jev**（TypeSafe 的快速决策模型，每次约 0.3 秒）：
  - 先看用户的话是不是正好和唯一一个按钮上的字一样，是就直接用，不调用模型。
  - 否则只把元素名字（绝不发输入框内容和密码）连同用户的要求发给 Jev，做一道选择题。
  - Jev 选中且置信度 ≥ 0.8 就点。
  - 不够就把前几个候选交回 DeepSeek 挑，或者问用户。
  - 没有 Jev key 时退回由 DeepSeek 挑。
- 安全：Jev 还会回答「这一步好不好撤销」。加上关键词规则（删除、发送、付款、退出登录、终端命令、退出快捷键……），有风险的步骤都出确认卡，用户明确说「好」才执行。其它保护：
  - 每轮最多 12 个动作。
  - 用户说「停」或按停止键时，看门狗立刻停掉「手」应用。
  - 绝不往密码框里输入。
  - 从屏幕上读到的文字只当数据，绝不当指令。
- 默认在后台安静操作。只有用户要求「展示给我看」时，才在屏幕上可见地操作。

## 真正让它变快的（按效果排序）

1. **合成模型常驻并预热。** 冷加载让第一句回答多花了 5.3 秒。服务启动时就加载，每次唤醒、开始听、用户说话时再预热一次。空闲 30 分钟才卸载。在 Apple MLX 上要设 `mx.set_cache_limit(...)`，不然内存会涨上去。
2. **全程流式。** 大模型的字流进分句器，每分好一段直接进流式合成，每块音频一出来就播。绝不等完整回答。
3. **按句切，不按逗号切。** 每个逗号片段单独合成听起来很碎，因为语调每次都重新起。对我们有效的规则：
   - 第一句超过约 24 个字才在逗号处切，这样第一声仍然来得早。
   - 短于约 14 个字的句子并到下一句。
   - 每段软上限约 60 个字。
4. **让提示词对缓存友好。** 固定内容放前面：人设、规矩、长期记忆。变化的内容（当前时间、实时数据）放最后，作为用户消息前一条单独的系统消息。我们的缓存命中率从约 3% 涨到约 50%，首字更快也更省钱。
5. **语音用快的非推理模型，并要求说短。** 语音轮次带一个标记，让模型用几句简短的口语回答，不用 markdown。
6. **一开始听就预加载识别模型**，趁用户还在说。声纹核对和识别解码并行，不要排在后面。
7. **按键说话松手就立刻结束这一轮**，不等 VAD 判断静音。
8. **发给合成的文字片段一次一个、按顺序发。** 并发发送会乱序，念出来是乱的。

## 踩过的坑和修法

- **助手听到了自己。** 说完以后，把自己的回声识别成了新问题。修法：
  - 播放结束后等约 0.7 秒再开接话窗口。
  - 这个窗口不带预录音频。
  - 没有回声消除时，助手说话期间不认单字的停止词。
- **插话（打断）。** 助手说话时按说话键：停止合成、取消大模型请求、马上开始听。在自动打开的接话窗口里按键表示「开始说」，不是「取消」。
- **macOS 回声消除（voice processing I/O）。**
  - 要先把播放节点接到混音器，再开 voice processing，否则报 -10875。
  - 开着时，别的用麦克风的应用（比如听写）收到的声音很小。
  - 最后我们平时关着它、正常共享麦克风，打断改用按键。
- **克隆音色的合成大约一半句子会跑成另一个（男）声音。** 改温度、种子、加长参考音频都没用。我们在播放前检查每块的音高，跑偏就换种子重新合成。内置的预设声音不会跑，不需要克隆声音就优先用预设。
- **停止事件在页面和语音服务之间来回循环**，按一次发出约 60 个「停」。修法：停止事件去重，刚收到的停止不要再转发回去。

## 请你对我的项目这样做

1. **先打点计时。** 给每个环节加时间戳：
   - 说完话
   - 最终文字出来
   - 发出大模型请求
   - 大模型第一个字
   - 第一块合成音频就绪
   - 第一声真正播出
   - 音频块之间的间隔

   每段合成记录：字数、首块用时、总合成时间、音频时长、实时率。
2. 跑 3–5 次真实对话，给我一张时间线表格，看时间花在哪。
3. 和上面的参考数字对比，先修最大的差距。通常依次是：
   - 模型冷加载
   - 没流式的环节
   - 按逗号切的合成
   - 会变的提示词前缀
   - 太长的 VAD 静音
   - 太慢的或推理型大模型
4. 每改一处就重新测，给我看前后对比。
5. 保持稳定：
   - 没有反馈循环。
   - 不能把自己的声音识别进来。
   - 不能挡住别的应用用麦克风。
